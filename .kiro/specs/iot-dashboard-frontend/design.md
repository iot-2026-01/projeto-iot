# Design Document — IoT Dashboard Frontend

## Overview

The IoT Dashboard Frontend is a React single-page application (SPA) that provides real-time monitoring and manual control of the Smart Load Balancing System. It polls the backend API every 2 seconds, renders live channel data (current readings, overload states, relay statuses), and exposes operator actions (relay override, channel current update, system reset).

**Technology stack:**
- React 18 + TypeScript 5
- Vite 5 (build tool + dev proxy)
- Tailwind CSS 3 (utility-first styling, no heavy UI library)
- Vitest + React Testing Library (unit/component tests)
- fast-check (property-based testing)

**Visual design:** Binance-inspired design system, defined in `/DESIGN.md` (generated by `npx getdesign@latest add binance`). All UI implementation must reference that file for colors, typography, spacing, and component tokens.

The frontend lives in a new `/frontend` directory at the project root, completely independent of the `/api` package.

## Architecture

### High-Level Structure

```
Browser
  └── React SPA (Vite)
        ├── useTelemetry hook  ──── polls every 2 s ──► GET /api/load-balancer/telemetry
        ├── API client module  ──────────────────────► POST /api/load-balancer/relay
        │                                             POST /api/load-balancer/channels
        │                                             POST /api/load-balancer/reset
        └── Component tree
              App
              ├── ErrorBanner
              ├── TelemetryPanel
              ├── OverloadPanel
              ├── ChannelCard × 3
              │     ├── RelayControl
              │     └── CurrentUpdateForm
              ├── ResetButton
              └── ConfirmDialog (portal)
```

### Dev Proxy

During development, Vite proxies all `/api` requests to `http://localhost:3000`, so the frontend can be served on a different port without CORS issues.

```
vite.config.ts
  server.proxy['/api'] → http://localhost:3000
```

### Data Flow

```
useTelemetry (setInterval 2 s)
  │
  ▼
loadBalancerApi.getTelemetry()
  │  success → setState({ data, error: null, loading: false })
  │  failure → setState({ error, loading: false })
  ▼
Context / prop drilling
  │
  ▼
ChannelCard, OverloadPanel, TelemetryPanel (read-only display)
RelayControl, CurrentUpdateForm, ResetButton (write actions)
  │
  ▼
loadBalancerApi.setRelay / updateChannel / resetSystem
  │  success → trigger immediate re-poll
  │  failure → local error state per component
```

## Components and Interfaces

### Component Tree

#### `App`
Root component. Owns the `useTelemetry` hook result and distributes data via props (or a lightweight context if prop drilling becomes unwieldy). Renders the full layout.

**Props:** none  
**State:** provided by `useTelemetry`

---

#### `useTelemetry` (custom hook)
Encapsulates all polling logic. Returns a stable object that components consume.

```typescript
interface UseTelemetryResult {
  data: TelemetryData | null;
  loading: boolean;
  error: TelemetryError | null;
  connectionUnavailable: boolean;
  triggerPoll: () => void;          // called after successful mutations
}
```

Internals:
- `setInterval` at 2 000 ms, cleared on unmount via `useEffect` cleanup.
- Each fetch is wrapped in `AbortController` with a 5-second timeout.
- On 3 consecutive failures the hook sets `connectionUnavailable = true`; cleared on next success.
- `triggerPoll` resets the interval timer and fires an immediate fetch.

---

#### `ErrorBanner`
Displays the current polling error (if any) at the top of the page. Distinguishes polling errors from control-action errors via a `type` prop.

```typescript
interface ErrorBannerProps {
  message: string | null;
  type: 'polling' | 'action';
  onDismiss?: () => void;
}
```

---

#### `TelemetryPanel`
Displays device ID, formatted uptime, event counter, and last-update timestamp.

```typescript
interface TelemetryPanelProps {
  data: TelemetryData | null;
  loading: boolean;
}
```

Formatting helpers (pure functions, tested with fast-check):
- `formatUptime(seconds: number): string` → `"Xh Ym Zs"`
- `formatTimestamp(date: Date): string` → `"YYYY-MM-DD HH:MM:SS"` in local timezone

---

#### `OverloadPanel`
Summarises overloaded channels. Derives its display purely from the `channels` array.

```typescript
interface OverloadPanelProps {
  channels: ChannelData[];
}
```

---

#### `ChannelCard`
Renders one channel's data and hosts its two control sub-components.

```typescript
interface ChannelCardProps {
  channel: ChannelData | null;   // null → "Data unavailable" placeholder
  disabled: boolean;             // true when connectionUnavailable
  onRelayChange: (channelId: string, state: boolean) => Promise<void>;
  onCurrentUpdate: (channelId: string, current: number) => Promise<void>;
}
```

The card root element carries `data-overload="true"` when `channel.overload === true`, enabling both CSS styling and test assertions.

---

#### `RelayControl`
Toggle button (Connected / Disconnected) for a single channel's relay.

```typescript
interface RelayControlProps {
  channelId: string;
  relayActive: boolean;
  disabled: boolean;
  onToggle: (channelId: string, newState: boolean) => Promise<void>;
}
```

Manages its own `pending` boolean to disable the button while the request is in flight.

---

#### `CurrentUpdateForm`
Numeric input + submit button for manually setting a channel's current.

```typescript
interface CurrentUpdateFormProps {
  channelId: string;
  disabled: boolean;
  onSubmit: (channelId: string, current: number) => Promise<void>;
}
```

Client-side validation: value must be a finite number in `[0, 999.99]`. Validation runs on submit; error is cleared when the field value becomes valid.

---

#### `ResetButton`
Triggers the confirmation flow and then the reset API call.

```typescript
interface ResetButtonProps {
  disabled: boolean;
  onReset: () => Promise<void>;
}
```

Manages its own `pending` boolean and a 10-second timeout guard.

---

#### `ConfirmDialog`
Modal confirmation dialog rendered via a React portal into `document.body`.

```typescript
interface ConfirmDialogProps {
  open: boolean;
  message: string;
  onConfirm: () => void;
  onCancel: () => void;
}
```

### API Client Module — `src/api/loadBalancer.ts`

All network calls are centralised here. Each function throws a typed `ApiError` on failure.

```typescript
// src/api/loadBalancer.ts

export interface ApiError {
  type: 'network' | 'timeout' | 'http';
  status?: number;           // present for 'http' errors
  message: string;
}

export async function getTelemetry(signal?: AbortSignal): Promise<TelemetryData>;

export async function getChannels(signal?: AbortSignal): Promise<ChannelData[]>;

export async function setRelay(
  channelId: string,
  state: boolean,
  signal?: AbortSignal
): Promise<ChannelData>;

export async function updateChannel(
  channelId: string,
  current: number,
  signal?: AbortSignal
): Promise<ChannelData>;

export async function resetSystem(signal?: AbortSignal): Promise<void>;
```

Error classification logic (pure, testable):
- `response.ok === false` → `ApiError { type: 'http', status, message }`
- `AbortError` from timeout → `ApiError { type: 'timeout', message }`
- `TypeError` (network) → `ApiError { type: 'network', message }`

## Data Models

### Shared Types — `src/types/index.ts`

These mirror the API's `types/index.ts` exactly:

```typescript
export interface ChannelData {
  channel: string;       // "A" | "B" | "C"
  currentAmps: number;
  overload: boolean;
  relayActive: boolean;
}

export interface TelemetryData {
  device: string;
  uptime: number;        // seconds
  events: number;
  channels: ChannelData[];
  timestamp: Date;       // parsed from ISO string on receipt
}
```

### Validation Rules (enforced client-side before API calls)

| Field | Rule |
|---|---|
| `channelId` | Must be `"A"`, `"B"`, or `"C"` |
| `current` | Finite number, `0 ≤ current ≤ 999.99` |
| `relayState` | Boolean |

### UI-Derived State

The following values are derived from `TelemetryData` at render time — they are never stored separately:

| Derived value | Source |
|---|---|
| Overloaded channel list | `channels.filter(c => c.overload)` |
| Overload count | `channels.filter(c => c.overload).length` |
| Formatted uptime | `formatUptime(telemetry.uptime)` |
| Formatted timestamp | `formatTimestamp(telemetry.timestamp)` |
| Relay label | `channel.relayActive ? "Connected" : "Disconnected"` |

## Correctness Properties

*A property is a characteristic or behavior that should hold true across all valid executions of a system — essentially, a formal statement about what the system should do. Properties serve as the bridge between human-readable specifications and machine-verifiable correctness guarantees.*


### Property 1: `formatUptime` correctness

*For any* non-negative integer number of seconds `s`, `formatUptime(s)` SHALL return a string of the form `"Xh Ym Zs"` where `X = Math.floor(s / 3600)`, `Y = Math.floor((s % 3600) / 60)`, and `Z = s % 60`. Specifically, `formatUptime(0)` SHALL return `"0h 0m 0s"`.

**Validates: Requirements 4.2**

---

### Property 2: `formatTimestamp` format correctness

*For any* valid `Date` object `d`, `formatTimestamp(d)` SHALL return a string that matches the pattern `YYYY-MM-DD HH:MM:SS` (where each component is zero-padded to its expected width) representing the date and time in the user's local timezone.

**Validates: Requirements 4.4**

---

### Property 3: ChannelCard renders all fields correctly

*For any* `ChannelData` value, the rendered `ChannelCard` SHALL:
- Display the channel identifier
- Display `currentAmps` formatted to exactly 2 decimal places followed by `"A"`
- Set `data-overload="true"` on the card root when `overload === true`, and `data-overload="false"` (or absent) when `overload === false`
- Display `"Connected"` when `relayActive === true` and `"Disconnected"` when `relayActive === false`

**Validates: Requirements 2.1, 2.2, 2.3, 2.4, 2.5**

---

### Property 4: OverloadPanel lists exactly the overloaded channels

*For any* array of `ChannelData`, the `OverloadPanel` SHALL display exactly the channel identifiers where `overload === true`. When no channel has `overload === true`, it SHALL display `"All channels normal"`. When one or more channels have `overload === true`, it SHALL display the count and each overloaded channel's identifier.

**Validates: Requirements 3.1, 3.2, 3.3**

---

### Property 5: Current value validation rejects out-of-range inputs

*For any* numeric value `v` that is negative, greater than `999.99`, `NaN`, or `Infinity`, the `CurrentUpdateForm` validation SHALL reject `v`, display a validation error message, and SHALL NOT invoke the API call. *For any* value `v` in `[0, 999.99]` that is a finite number, the validation SHALL accept `v`.

**Validates: Requirements 6.3**

---

### Property 6: Relay control invokes API with correct parameters

*For any* valid channel identifier `channelId ∈ {"A", "B", "C"}` and boolean `state`, when the operator activates the relay control, the `setRelay` API function SHALL be called with exactly `(channelId, state)`.

**Validates: Requirements 5.2**

---

### Property 7: Channel update invokes API with correct parameters

*For any* valid channel identifier `channelId ∈ {"A", "B", "C"}` and finite number `current ∈ [0, 999.99]`, when the operator submits the current update form, the `updateChannel` API function SHALL be called with exactly `(channelId, current)`.

**Validates: Requirements 6.2**

---

### Property 8: HTTP error display includes status code and message

*For any* HTTP error with status code `s ∈ [400, 599]` and error message string `m`, the error display rendered by `ErrorBanner` SHALL include both the numeric status code `s` and the message string `m` in its visible text.

**Validates: Requirements 9.1**

---

### Property 9: Polling and control-action errors carry distinct labels

*For any* polling error and *for any* control-action error (relay, channel update, or reset), the label or prefix displayed in the UI for the polling error SHALL be textually distinct from the label displayed for the control-action error.

**Validates: Requirements 9.4**

---

## Error Handling

### Error Classification

All errors are classified at the API client layer (`src/api/loadBalancer.ts`) before reaching components:

| Condition | `ApiError.type` | UI treatment |
|---|---|---|
| `fetch` throws `TypeError` | `'network'` | "Connection unavailable" banner |
| `AbortController` timeout (5 s) | `'timeout'` | "Request timed out" banner + connectionUnavailable state |
| HTTP 4xx response | `'http'` | Error banner with status code + API message |
| HTTP 5xx response | `'http'` | Error banner with status code + API message |

### Polling Errors vs. Control-Action Errors

- **Polling errors** (from `useTelemetry`) are displayed in the top-level `ErrorBanner` with a "Data refresh failed:" prefix. They do not block the UI.
- **Control-action errors** (relay, channel update, reset) are displayed inline near the triggering control with a component-specific prefix (e.g., "Relay error — Channel A:", "Update error — Channel B:"). They persist until the next successful request for that channel or until dismissed.

### Connection Unavailable State

The `useTelemetry` hook tracks consecutive failures. After 3 consecutive polling failures (or any timeout), it sets `connectionUnavailable = true`. This state:
- Disables all relay controls (Req 5.7)
- Shows a persistent "Connection unavailable" banner
- Is cleared on the next successful poll (Req 9.5)

### Timeout Guards

- **Polling requests**: 5-second `AbortController` timeout per fetch (Req 1.3, 9.2)
- **Reset action**: 10-second timeout guard in `ResetButton`; if the request does not complete within 10 s, the button is re-enabled and a timeout error is shown (Req 7.7)

### Validation Errors

Client-side validation in `CurrentUpdateForm` runs before any API call. Invalid inputs (out of range, non-numeric) display an inline error message and suppress the API call entirely (Req 6.3). The error clears as soon as the field value becomes valid (Req 6.4).

- No left border (or a 4px `hairline-on-dark` border)
- Current reading in `trading-up` (`#0ecb81`) to signal healthy state

## Testing Strategy

### Dual Testing Approach

The testing strategy combines example-based unit tests and property-based tests for comprehensive coverage.

**Unit tests** (Vitest + React Testing Library) cover:
- Specific rendering examples (device ID, event counter, placeholder states)
- State transitions (error → success clears banner, overload → normal removes from panel)
- User interaction flows (confirm/cancel reset dialog, relay toggle pending state)
- Edge cases (null channel prop → "Data unavailable", loading state before first poll)

**Property-based tests** (fast-check, minimum 100 iterations each) cover the 9 correctness properties defined above.

### Property-Based Testing Configuration

Library: **fast-check** (`npm install --save-dev fast-check`)  
Runner: **Vitest**  
Minimum iterations: **100** per property (fast-check default is 100; set explicitly via `{ numRuns: 100 }`)

Each property test is tagged with a comment referencing the design property:

```typescript
// Feature: iot-dashboard-frontend, Property 1: formatUptime correctness
it('formatUptime returns correct Xh Ym Zs for any non-negative seconds', () => {
  fc.assert(
    fc.property(fc.nat(), (seconds) => {
      const result = formatUptime(seconds);
      const h = Math.floor(seconds / 3600);
      const m = Math.floor((seconds % 3600) / 60);
      const s = seconds % 60;
      expect(result).toBe(`${h}h ${m}m ${s}s`);
    }),
    { numRuns: 100 }
  );
});
```

### What Is Not Unit-Tested

- Responsive layout (Req 8): requires browser/visual regression testing
- Polling interval timing (Req 1.1, 1.2): covered by fake-timer smoke tests
- 100 ms update latency (Req 2.6): covered by React's synchronous rendering
- Vite proxy configuration: verified by running the dev server manually
